Why a retry budget saves a slow host

Two clients send the same 80 requests per second to the same host. At 8 s the host slows down and can serve only 60 per second. At 24 s it is fixed. Both clients retry failed requests up to 3 times. Only the right one has a retry budget. Press Play. The page slows down at key moments and says what happened.

Why plain retries never let go

  1. The host slows down. Requests wait longer than the client's timeout, so the client counts them as failures.
  2. Every failure comes back as a retry, up to 3 times. One request can become 4 attempts.
  3. The host now gets about 3.6× its normal traffic. It spends time on requests whose clients already gave up, so it serves even fewer.
  4. Fewer served means more failures, which means more retries. The loop feeds itself.

Look at the left lane after the host is fixed. It can serve 120/s again, but the retries keep sending it more than that, so it stays down. This is called a metastable failure: the original cause is gone, and the retries alone keep the outage going.

What the budget changes

The budget doesn't look at whether a single request deserves a retry. It looks at the whole partition: retries may add at most ratio on top of the first attempts seen in the last windowMs.

allowed = max(minRetriesPerSec × windowMs/1000, ratio × firstAttemptsInWindow) retry allowed only while retriesInWindow < allowed

With ratio: 0.1, the host gets at most about 1.1× its normal load, however bad things get. Refused retries fail right away with their last error, so the caller hears about it quickly instead of waiting. As soon as the host is fixed, load is already below capacity and everything succeeds.

Try moving the sliders: with 1 max retry, even the left lane recovers. With a budget ratio of 0.5, the right lane carries more load during the outage.

In Vereda

HttpClient.create({ timeout: { attemptMs: 1_000 }, retry: { maxRetries: 3 }, retryBudget: { ratio: 0.1, windowMs: 1_000, minRetriesPerSec: 1, }, })
