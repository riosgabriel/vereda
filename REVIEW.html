High

#1

Relative URL without baseUrl throws synchronously

verified

src/core/client.ts:87

new URL(fullUrl).hostname picks the partition. With no baseUrl, a relative path is an invalid URL and client.get("/users/1") throws TypeError: Invalid URL before a ticket is returned. The README's first code block is exactly this case, and it breaks the "toPromise() never rejects" contract — this is the one error a caller must try/catch. 

HttpClient.create().get("/users/1")  →  throws "Invalid URL"

Suggestion Resolve the partition inside the async path so the error lands in the ticket as a Result (a ConfigurationError), or validate in request() and return an already-failed ticket. Add baseUrl to the README example.

#2

"Global concurrency" is the per-partition default

verified

src/core/client.ts:28-31 · src/queue/bulkhead.ts:99-102

{ concurrency: config.concurrency ?? 10 } is passed as the global PartitionConfig and spread into every partition. There is no cross-partition cap anywhere: 8 partitions × 10 = 80 concurrent retries. The README defaults table says per-partition concurrency is 5; that Bulkhead default is unreachable from HttpClient, so the real default is 10. 

HttpClient.create({ concurrency: 10 }) → partition "a.example".concurrencyLimit = 10   (docs: 5)

Suggestion Implement a real global semaphore each bulkhead acquires before running (global cap and per-partition cap, both enforced) and rename the per-partition default to defaultPartition: PartitionConfig. Generate the README defaults table from code.

#3

retry lifecycle event is never emitted

verified

src/core/types.ts:87 · src/core/client.ts (no emit site)

LifecycleEventMap.retry is typed and documented, but grep '"retry"' src/ returns nothing. client.on("retry", …) never fires, so fleet-level retry metrics — the stated purpose of lifecycle events — are impossible. 

maxAttempts=12, all 429 → 'retry' lifecycle events emitted: 0

Suggestion runRetryLoop takes an onRetry(attempt, delayMs, error) callback invoked beside ticket._markRetrying. Add a test asserting event count equals retry count.

#4

Busy status codes surface as TimeoutError

verified

src/core/client.ts:166-169 · src/queue/retry.ts:75-77

queued_status is collapsed into new TimeoutError(url, timeoutMs ?? 0). A 429 with no timeout configured yields "timed out after 0ms". retryWhen cannot express "retry on 429 but not on timeout", lastError misreports what happened, and the Response (with any Retry-After) is dropped. Commit a6b4c0c added a RetryableStatusError for this and was reverted in 19bbf2c. 

503 ×4, queueOnStatus:[503] → lastError = TimeoutError "timed out after 1000ms"

Suggestion Add RetryableStatusError { statusCode, response, retryAfterMs? } to the AppError union; honor Retry-After (R1).

#5

Bulkhead slot held during backoff sleep

verified

src/core/client.ts:218-242 · src/queue/retry.ts:44

The entire runRetryLoop runs as one bulkhead.schedule() task, so await sleep(delayMs) holds the slot. With the default 30 s cap, a partition of concurrency 5 can have all 5 slots occupied by tickets doing nothing. The README describes the limit as "in-flight retries"; it is really "retry loops, including their idle time". 

concurrency:1, two failing tickets, baseDelayMs:300 → during sleep: running=1 queued=1

Suggestion Schedule each attempt through the bulkhead and sleep outside it (release → sleep → re-acquire) so slots are always doing network work.

#22

Unsafe retry defaults: non-idempotent methods, 4xx, stream bodies

verified

src/queue/retry.ts · src/queue/executor.ts:94-101, 147-156

  • Non-idempotent methods are retried. post()/patch() use the same loop as GET. A POST that timed out after the server processed it is replayed up to 3 more times by default — duplicate orders, duplicate payments. Nothing warns about this.
  • All non-2xx are retried. A 404 or 400 is retried 4 times with backoff. Client errors are deterministic; retrying wastes the latency budget and server capacity. The README states "all non-2xx responses are retried" as if it were a feature.
  • Stream bodies fail on every attempt. A ReadableStream body is rejected by undici without duplex: "half"; the TypeError becomes a NetworkError and is retried 4 times. Even with duplex, a one-shot stream is consumed on attempt 1 and replayed empty. 
404 → server hits: 4 | MaxRetriesExceededError
POST with ReadableStream body → MaxRetriesExceededError, server received 0 bodies

Suggestion Conservative default policy: retry network errors, timeouts, 408/425/429/5xx; never other 4xx; retry non-idempotent methods only on opt-in (retry: { idempotent: true } or an Idempotency-Key header). Reject ReadableStream bodies with a ConfigurationError unless a body: () => BodyInit factory is supplied. Document as a "What gets retried" table (D2).

Medium

#6

First retry has zero backoff and no retrying update

verified

src/queue/retry.ts:31

Backoff and _markRetrying only apply when attempt > 0, but loop iteration 0 is already the second execution. The first retry fires 6 ms after queuing with no backoff and no event — for queueOnStatus: [429] the client immediately re-hits a server that just said "slow down". With maxAttempts: 1 the stream is just queued, done.

Suggestion Treat every loop iteration as a retry: backoffFn(attempt) and _markRetrying(attempt + 1, …).

#7

Abort listeners accumulate and are never removed

verified

src/queue/executor.ts:173-183 · src/core/client.ts:81

mergeSignals adds { once: true } listeners to the ticket signal and options.signal on every attempt; they fire only on abort, so on success or exhaustion they persist. The client also adds a listener to the caller's signal that is never removed when the ticket resolves. A long-lived shared signal (e.g. server shutdown) grows without bound. 

maxAttempts=8 → 9 listeners on ticket.signal; 10 on the caller's AbortSignal after done

Suggestion Use AbortSignal.any() (Node ≥ 20) or return a cleanup from mergeSignals called in finally; drop the external listener in _markDone/cancel.

#8

MaxRetriesExceededError.attempts off by one

verified

src/queue/retry.ts:88

Passes maxAttempts, but total executions are maxAttempts + 1. Message says "failed after 3 attempts"; the server received 4 requests. README says "maxAttempts: 3 → 4 total executions", so error and docs disagree.

Suggestion Report total executions, and rename to maxRetries (or make maxAttempts mean total) so the name matches the number — before 1.0, since it is breaking.

#9

timeoutMs does not cover body reading

src/queue/executor.ts:55-59, 108

The timeout is cleared once headers arrive; response.json() runs with no deadline and outside any signal. A server that sends headers then trickles the body hangs the ticket indefinitely whenever parse is set.

Suggestion Keep the timeout signal alive until the body is consumed; add totalTimeoutMs for the whole ticket (R3).

#10

Result<T>.data lies without parse

src/queue/executor.ts:136

Returns data: undefined typed as T. client.get<User>("/u") makes result.data.name a string to the compiler and a TypeError at runtime.

Suggestion Overloads: get(url) → Ticket<undefined>; get(url, { parse }) → Ticket<T>.

#11

Middleware cannot see the URL

src/queue/executor.ts:144-156 · README "Middleware"

MiddlewareFn receives RequestOptions, which has no url. The README example console.log("Request:", options.url) is a type error for anyone who copies it, and middleware cannot rewrite URLs (signing, prefixes).

Suggestion Pass a request object { url, method, headers, body, signal, attempt, ticketId } that middleware may modify (A2).

#12

Queue-full is an anonymous NetworkError

src/core/client.ts:244

Bulkhead rejection becomes NetworkError("Bulkhead 'x' queue is full …") with no statusCode. Callers cannot separate local backpressure from a network failure without string matching; retryWhen never sees it.

Suggestion QueueFullError { partition, queueSize, maxQueueSize } in the AppError union.

#13

Lifecycle event inconsistencies

src/core/client.ts:107-115, 141-143, 232

  • success after retries carries attempt: -1 as a sentinel; the type says number.
  • Cancellation emits no lifecycle event, so a metrics consumer sees request with no terminal event.
  • The catch-all in request() resolves the ticket but emits no failure.

Suggestion Exactly one terminal event per ticket (success | failure | cancelled) carrying attempts, durationMs, partition (O1).

#23

PartitionConfig.trigger/retry ignored; no config validation

verified

src/core/types.ts:46-53 · src/core/client.ts:25-36

PartitionConfig declares trigger and retry; the README admits they are "currently ignored". A type that accepts settings that do nothing is a trap. Nothing validates configuration either: negative concurrency, maxQueueSize: 0, timeoutMs: -1, baseDelayMs > maxDelayMs are accepted silently. 

maxAttempts: 0 → MaxRetriesExceededError "Request failed after 0 attempts: … timed out after 0ms"

Suggestion Implement the global → partition → request merge (the reverted a6b4c0c did) or remove the fields. Validate in HttpClient.create() and throw ConfigurationError naming the key — construction time is the one place throwing is right.

#24

Partition key ignores the port

verified

src/core/client.ts:87

Bulkheads are keyed by hostname. http://svc:8080 and http://svc:9090 are different services but share one queue and concurrency limit; the failure of one throttles the other.

Suggestion Key by origin (scheme + host + port) by default; keep partition as the explicit override.

#17

  • AGENTS.md:25 "claims 36 tests; suite has 30" — both stale; the suite has 40 and README says 40.
  • GOOD_FIRST_ISSUES.md #1 asks a newcomer to change "36" to "30" — obsolete, in a file that promises every item is verified.

#18

Ticket.off() signature mismatch

src/ticket/ticket.ts:84

on() accepts (result: Result<T>) => void; off(event, listener: (...args: unknown[]) => void) rejects that function under strictFunctionTypes. Mirror the overloads.

#19

Bulkhead snapshot not exposed

src/queue/bulkhead.ts:108

BulkheadRegistry.getAll() returns { running, queued, concurrency, maxQueueSize } but HttpClient.bulkheads is private. It is the only way to see backpressure before it becomes queue-full errors.

#20

Unconsumed response bodies

src/queue/executor.ts:89-101

On queued_status and non-2xx the Response is dropped or returned without body.cancel(). Undici keeps the connection busy until the body drains or is GC'd; sustained 429s can hold sockets.

#21

Test coverage gaps

Nothing exercises: queue-full through HttpClient; the retry lifecycle event (#3); partition config through the client (#2); defaultHeaders/requestLogger; subscribe() on a terminal ticket; Ticket.off(); relative URLs (#1); the attempts value (#8); POST retry semantics (#22).

#25

Internal ticket mutators are public API

src/ticket/ticket.ts:148-166

_markDone, _markQueued, _markRetrying are public methods on the exported class; any consumer or middleware can resolve someone else's ticket. Move them behind a module-private symbol or a TicketController handed only to the client; mark @internal and enable stripInternal.

Part 2

Production readiness

Fixing Part 1 gives a correct library. The items below separate "correct" from "I would put this in front of production traffic and sleep at night". Each is concrete enough to become an issue.

R · Resilience semantics

R1

Honor Retry-After

When a 429/503 carries Retry-After (seconds or HTTP-date), use it as that retry's delay (capped by maxDelayMs) instead of the computed exponential value. Requires #4 so the response reaches the retry loop.

R2

Conservative, documented default retry policy

Retry: network errors, timeouts, 408, 425, 429, 5xx. Do not retry: other 4xx, ValidationError, non-idempotent methods without opt-in. Export defaultRetryPolicy so users extend rather than rewrite it (#22).

R3

Total deadline

Add totalTimeoutMs for the whole ticket (all attempts plus queue time) alongside the per-attempt timeoutMs. Without it, maxAttempts: 5 with a 30 s cap can take minutes. The ticket resolves with a DeadlineExceededError when it fires, even while queued.

R4

Retry budget

Per-partition budget ("retries may be at most 20% of requests over a sliding window") prevents retry storms when a dependency is fully down — where exponential backoff alone is not enough. Opt-in, off by default.

R5

Circuit breaker (optional)

With #19 exposing partition health, a simple breaker (open after N consecutive failures, half-open probe after cooldown) is a small addition and the most-requested feature of this class of library. Opt-in per partition.

R6

Bulkhead for first attempts (opt-in)

Keep the unbounded-first-attempt default, but offer limitFirstAttempts: true per partition for callers who need a hard cap on connections to a fragile dependency.

O · Operability

O1

One terminal event per ticket, with timings

success/failure/cancelled carry attempts, durationMs, queuedMs, partition, statusCode — what a metrics adapter needs (#13).

O2

Metrics adapter surface

client.on(…) suits logs, not metrics. Provide a MetricsSink interface (counter, histogram, gauge) fed by the client plus partition gauges from #19. Ship an OpenTelemetry example.

O3

Structured, redacted logging

The logger receives full URLs; query strings often carry tokens. Redact query parameters by default, never log headers. Use the unused debug level for per-attempt detail so info stays quiet in production.

O4

Graceful shutdown

client.close({ drain?, timeoutMs? }): stop accepting requests, optionally wait for in-flight tickets, cancel the rest, clear timers. unref() backoff timers so a pending retry never keeps a process alive.

O5

Injectable fetch

HttpClient.create({ fetch }) — needed for undici Agent tuning (keep-alive, connection limits, proxies), socket-free tests, and platforms whose global fetch differs. Also the cleanest place for tracing headers.

A · API and type surface

A1

Freeze the error model

Add a string kind discriminant to every AppError ("network" | "timeout" | "retryable_status" | "validation" | "cancelled" | "max_retries" | "queue_full" | "configuration"). instanceof fails across duplicated bundles; a discriminant does not. Keep the classes for stack traces.

A2

Request object for middleware

{ url, method, headers: Headers, body, signal, attempt, ticketId }; middleware may return a modified request. Accept HeadersInit and merge case-insensitively — defaultHeaders currently produces both authorization and Authorization (#11).

A3

Honest generics

Ticket<undefined> without parse, Ticket<T> with it (#10).

A4

Replayable bodies

Accept body: BodyInit | (() => BodyInit); reject ReadableStream without a factory (#22).

A5

Hide internals and settle names before 1.0

#25; maxAttempts vs maxRetries (#8); hostname vs origin default (#24); concurrency vs defaultPartition.concurrency (#2). Every one of these is a breaking change afterwards.

A6

Conveniences production code needs

head(), options(); a JSON shortcut (parse: json<T>()) so the common case needs no schema library; AbortSignal.timeout() interop.

P · Packaging and release

P1

Publish to npm

Installing from GitHub runs prepare → tsc on every consumer's machine, needs devDependencies, and makes files: ["dist"] meaningless. 1.0 should be npm install vereda with a prebuilt dist/, a tag per release, GitHub Releases, and npm provenance from CI.

P2

package.json hygiene

exports with "types" first; "sideEffects": false; "engines": { "node": ">=20" }; repository, bugs, homepage; drop main/types in favour of exports. Run publint and @arethetypeswrong/cli in CI.

P3

Node support policy

Drop 18 (EOL); test 20, 22, 24; state the policy in the README. Unlocks AbortSignal.any (#7) and Promise.withResolvers.

P4

Versioning and changelog

Explicit semver, CHANGELOG.md (Keep a Changelog), and a written definition of what counts as breaking (error names, event payloads, defaults). Consider changesets.

P5

Reproducible installs

Pick one package manager. pnpm: pnpm/action-setup + --frozen-lockfile in CI and fix #14. npm: commit package-lock.json and use npm ci.

Q · Quality gates

Q1

CI runs everything

Typecheck, lint, prettier --check, tests with coverage, build, publint. Fail on no-explicit-any warnings (#15).

Q2

Coverage threshold

@vitest/coverage-v8 with a floor (e.g. 90% lines on src/); the gaps in #21 are where the bugs were.

Q3

Deterministic timing tests

vi.useFakeTimers() for backoff/timeout tests instead of real 10 ms sleeps; timing tests are the first to flake on shared CI runners.

Q4

Behavioral test matrix

One integration test per row of the "what gets retried" table (R2): method × status × body type × idempotency flag. This is the contract users depend on; it should be executable.

Q5

Concurrency and leak tests

Listener counts return to baseline after a ticket resolves (#7); bulkhead running returns to 0 during backoff (#5); a global cap holds across partitions (#2).

D · Documentation

D1

Fix contradictions

Hero example needs baseUrl (#1); defaults table (#2); middleware options.url (#11); test counts and .claude/skills (#17). Generate the defaults table from code in a test so it cannot drift again.

D2

"What gets retried" table and idempotency warning

Near the top of the README — the single most important thing a production user needs to know.

D3

API reference

TypeDoc from the @internal-stripped declarations, published to GitHub Pages. JSDoc every public option with its default.

D4

Operations guide

Sizing concurrency/maxQueueSize, choosing timeoutMs vs totalTimeoutMs, reading partition snapshots, wiring metrics, shutdown sequence.

D5

Update the internal docs

AGENTS.md "Gotchas" and ONBOARDING.md must reflect the new invariants: per-attempt bulkhead scheduling, retry policy, error kinds.

Release gate

1.0.0 definition of done

Ordered so that each step unblocks the next.

  • Unblock local dev and the README — #1, #14, #17 (D1).
  • Retry loop correctness — #3, #6, #8, #16, #25; tests for each (Q5).
  • Error model — #4, #12, #23 (ConfigurationError), A1 kind discriminant; re-land the intent of a6b4c0c.
  • Safe defaults — #22 / R2 policy, A4 replayable bodies, R1 Retry-After; D2 table; Q4 matrix.
  • Resource correctness — #7, #9, #20, O4 shutdown + unref.
  • Concurrency semantics — #2 real global cap, #5 per-attempt scheduling, #24 origin key, #19 snapshot exposed; Q5 tests.
  • Deadlines — R3 totalTimeoutMs.
  • Observability — #13 / O1 terminal events with timings, O2 metrics sink, O3 redaction, O5 injectable fetch.
  • API freeze — A2, A3, A5 naming decisions, A6 helpers, Ticket.off() (#18). Publish 1.0.0-rc.1.
  • Packaging and CI — P1–P5, Q1–Q3, #15.
  • Docs — D3 API reference, D4 operations guide, D5 internal docs, CHANGELOG with the 1.0.0 entry.
  • Optional for 1.0, recommended for 1.x — R4 retry budget, R5 circuit breaker, R6 first-attempt limiting.

What is already solid

The ticket state machine ignores illegal transitions, makes double resolution impossible, and treats cancel() as terminal — all tested. Cancel-vs-timeout precedence in executeRequest is correct and covered by three focused tests. ValidationError short-circuiting and retryWhen(…, 0) on the first failure match the documented invariants. Middleware composition is correct. The zero-dependency core, ESM-only stance, and self-contained node:http integration tests are the right foundations to build 1.0 on.
